# 《院长模拟器》V2 架构与内容说明

> 更新日期：2026-04-27 | 版本：V2（ES Module 三模块架构）

---

## 1. 项目定位

- **产品形态**：基于 ES Module 的 HTML5 文字策略模拟游戏，原生 JavaScript 实现，零外部依赖。
- **主题体验**：玩家扮演高校系主任/院长，在 8 学期（24个月）任期内平衡 5 项核心数值（经费、学术声望、行政信誉、教师士气、学生评价）及个人精力。
- **核心卖点**：
  - 事件驱动叙事 + 排程执行系统（Action Queue + Timeline Execution）；
  - 数值经营与风险管理并行，包含月度排程、随机事件、个人插曲；
  - 下属能力与忠诚影响执行效果；
  - 打字机效果叙事、数值变化 Toast 动画、进度条时间轴等沉浸式体验；
  - 存档/读档、成就/称号系统、周目累计数据；

---

## 2. 整体技术架构

### 2.1 架构风格

- **架构**：ES Module 原生模块化架构（`type="module"`），逻辑分三模块 + 一个入口 HTML 文件。
- **渲染方式**：基于模板字符串 + `innerHTML` 的手动渲染，关键渲染节点包含渐入/渐出动画。
- **状态管理**：单一全局对象 `v2` 作为状态源。
- **事件处理**：DOM 事件监听器（`addEventListener` + onclick 混合）。
- **流程控制**：通过 `v2.gameOver` / `v2.executionMode` / `v2.currentEvent` 等多重标志进行界面分流。

### 2.2 文件结构

```
Dean_simulator/
├── index.html                  # 入口页面（ES Module <script> 加载 game.js）
├── assets/
│   ├── css/
│   │   └── game.css            # 全部样式（506行，含动画关键帧）
│   ├── js/
│   │   ├── game.js             # 游戏引擎核心（~1350行）
│   │   ├── config.js           # 配置数据（院系/培养方案/下属/成就/难度/称号等）
│   │   └── events.js           # 事件系统（固定事件/随机事件/评论/叙事模板等）
│   └── fonts/
└── 游戏架构与内容说明.md        # 本文档
```

## 3. 模块划分详解

### 3.1 `config.js` — 配置与数据定义

- **导入方式**：被 `game.js` 和 `events.js` 导入。
- **覆盖内容**：

| 配置项 | 说明 |
|--------|------|

| `BACKGROUND_POOL` | 开局叙事背景池 |
| `STAFF_TEMPLATES` | 下属岗位模板（教学副院长/学术副院长/教务主任/实验室主任） |
| `STAFF_PERSONA_POOL` | 下属人设池（每人设多组随机人设：姓名、特质、能力/忠诚范围、简介、缺陷、任务线） |
| `DEPT_CONFIG` | 院系配置（数学/物理/计算机，含图标与初始数值修正） |
| `CURRICULUM_PASSIVE` | 培养方案被动成长（理论/应用/均衡） |
| `OFFICE_DECOR` | 办公室装饰数据 |

| `ACHIEVEMENTS` | 成就定义（含条件函数与周目点数） |
| `DIFFICULTY_PRESETS` | 难度预设（简单/普通/困难，含初始修正） |

- **覆盖内容**：

| `TEACHER_COMMENTS` | 教师评论池 |
| `LEADERSHIP_COMMENTS` | 校领导评论池 |

## 4. 数据流与核心循环

### 4.1 开局流程

```
DOMContentLoaded
  → v2HasSave('auto')? 检测存档 → 存档菜单
  → v2RenderSetup() → 步骤0~4（开场叙事/院系/培养方案/难度/姓名）
  → v2InitGame()
      ├── 应用 DEPT_CONFIG 初始修正
      ├── 应用 DIFFICULTY_PRESETS 初始修正
      ├── 生成随机下属（STAFF_TEMPLATES × STAFF_PERSONA_POOL）
      └── v2RenderPlaying()
```

### 4.2 主游戏循环

```
v2RenderPlaying()
  ├── 状态栏（5项数值 + 进度条）
  ├── 排程队列（actionQueue 可视化）
  ├── 行动 Tab（日常/重点/下属互动）
  └── 管理层面板 + 消息面板

玩家操作：
  1. 选择行动加入排程（v2AddAction）
  2. 点击「执行本月排程」（v2ExecuteMonth）
      └── v2RenderExecution()
          ├── 构建时间线（开场叙事 → 日常任务 → 重点任务 → 个人插曲 → 收尾）
          ├── 执行每一步（v2ExecNextStep）
          │   ├── 叙事/评论：打字机显示
          │   ├── 任务执行：v2ResolveTask + 数值变化 Toast
          │   ├── 随机事件弹窗（15%概率触发）
          │   └── 个人插曲（每学期首次60%概率）
          └── v2ExecFinish()
              ├── 应用培养方案被动加成
              ├── 解锁称号/成就
              ├── 重置月度资源（精力/天数/排程）
              ├── v2CheckEndings() 检测结局
              └── v2ShowMonthRecap() → v2ContinueGame() → v2RenderPlaying()
```

### 4.3 结局触发分支

```
v2CheckEndings() 在以下时机被调用：
  - 每次执行完成月度结算（v2ExecFinish）
  - 跳过剩余天数时（v2EndTerm）

触发条件：
  1. 经费 ≤ -10  → 财务危机（提前结束）
  2. 士气 ≤ 0    → 众叛亲离（提前结束）
  3. 总月数 ≥ 24 → 任期结束（正常完结）
  4. 学术 ≥ 85 且 经费 ≥ 75 → 高升结局
  5. 学生评价 ≥ 85 且 士气 ≥ 75 且 学术 ≥ 70 → 桃李满天下
```

## 5. 关键系统说明

### 5.1 天数经济（Action Queue 排程系统）

- **月度天数**：基础 28 天（办公室装饰可 +2 天）。
- **排程约束**：每月至少排 1 项日常 + 1 项重点任务方可执行。
- **执行过程**：按日常→重点顺序执行，每一步消耗任务指定天数，插入叙事/评论/个人插曲/随机事件。
- **跳过功能**：`v2EndTerm()` 直接进入下个月（跳过剩余天数，仅应用被动加成）。

### 5.2 数值系统

```
经费：[-20, 100]  学术/行政/士气/学生：[0, 100]  精力：[0, 100]
```

- **初始值**：所有数值从 30 开始（受院系/难度修正）。
- **被动成长**：培养方案每月结算时自动应用（理论→学术+2，应用→学生+2，均衡→各+1）。
- **精力重置**：每月重置为 100，下属谈心消耗 10。

### 5.3 下属系统

- **4 个岗位**：教学副院长、学术副院长、教务主任、实验室主任。
- **随机人设**：每人从 `STAFF_PERSONA_POOL` 随机抽取一组（姓名/特质/能力/忠诚/简介/缺陷）。
- **忠诚提升**：通过下属互动 Tab 谈心，消耗 10 精力，随机提升 3-10 忠诚。
- **能力调用**：当前版本中下属能力未直接参与任务执行效果计算，但为后续"放权 vs 亲力亲为"决策张力预留了基础。

### 5.4 初始差异化

| 院系 | 图标 | 初始修正 |
|------|------|----------|
| 数学系 | 🧮 | 学术 +5，经费 -10 |
| 物理系 | 🔭 | 无额外修正（均衡模板） |
| 计算机系 | 💻 | 经费 +10，学生 +5，学术 -5 |

### 5.5 培养方案

| 方案 | 月度结算加成 |
|------|-------------|
| 理论扎实型 | 学术 +2 |
| 应用技能型 | 学生评价 +2 |
| 均衡培养 | 学术 +1，学生评价 +1 |

### 5.6 难度系统

| 难度 | 初始修正 |
|------|----------|
| 简单 | 所有数值 +10 |
| 普通 | 无修正 |
| 困难 | 经费 -10，士气 -10 |

### 5.7 成就/称号系统

- **周目元数据**：通过 `v2MetaLoad/v2MetaSave` 持久化到 localStorage（周目点数、已解锁成就、最高分、总运行次数）。
- **成就条件**：在 `ACHIEVEMENTS` 数组中定义条件函数（如 `low_fund_meeting` 等）。
- **称号规则**：在 `TITLE_RULES` 数组中定义条件函数（基于当前 `v2` 状态）。

## 7. 代码可维护性评价

### ✅ 优点

1. **模块化架构清晰**：`config.js` 负责数据、`events.js` 负责内容、`game.js` 负责引擎，三者职责分明。
2. **状态集中管理**：单一 `v2` 对象作为状态源，便于调试和序列化（存档直接 `JSON.stringify`）。
3. **事件数据结构统一**：各种事件池共享相同的结构（title/text/choices/effect/feedback），扩展成本低。
4. **配置数据外置**：院系、培养方案、难度、成就、称号等数据在 `config.js` 中集中管理，无需修改引擎逻辑即可调整平衡。
5. **存档系统完善**：支持 3 个手动存档位 + 1 个自动存档位，周目元数据持久化。
6. **动画与视觉效果丰富**：页面过渡、数值闪烁、Toast 通知、打字机效果、进度条时间轴。

### ⚠️ 问题与局限

1. **全局命名空间污染**：通过 `window.xxx` 暴露大量全局函数（约 20 个），不利于模块化封装和树摇优化。
2. **渲染效率偏低**：`innerHTML` 全量重绘，频繁调用 `v2RenderPlaying()` 导致页面闪烁（虽有 `v2RenderQueueOnly` 部分优化但仍不够彻底）。
3. **事件数据硬编码**：随机事件池虽分模块但仍硬编码在 `events.js` 中，不利于策划编辑或动态加载。
4. **缺少日志系统**：游戏过程无操作日志记录，玩家难以回溯决策过程。
5. **缺少自动化测试**：回归验证完全依赖手动试玩。
6. **执行引擎耦合过深**：`v2RenderExecution()` 中时间线构建、叙事展示、数值变更、Toast 动画、弹出事件等耦合在一起，约 250 行。
7. **数值平衡未验证**：缺乏数据埋点，难以评估各选项/事件的收益平衡性。
8. **无响应式布局**：当前 CSS 布局未适配移动端。

### 🔧 已知需修复的 Bug

- **`v2CalcAvailableDays` 中咖啡机装饰双重计数**：`v2DefaultState()` 中 `availableDays` 初始写死 `28+2`，而 `v2CalcAvailableDays()` 也会检查 `officeDecor` 加 2，两者叠加导致初始可用天数多计 2。
